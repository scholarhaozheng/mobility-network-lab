Reproduction guide

Start with an exact experiment, then follow its data, environment, run and verification instructions. The Experiment catalog brings the original and subsequently integrated workflows into one place; each record selects the correct commands for you.

1. Download and extract

The single ZIP contains registered computational source, packaged frozen inputs, configuration and verification receipts. Extract it once into a new directory. No ZIP merging or Git installation is required. Python packages and native solver binaries are installed separately; records that require external inputs identify those inputs before the run step.

The download manifest above provides the exact archive size and checksum.

In Windows PowerShell, open the directory containing the downloaded ZIP and run:

if (Test-Path -LiteralPath .\mobility-reproduction) { throw 'Choose a new empty destination.' }
Expand-Archive -LiteralPath .\computational-checkout.zip -DestinationPath .\mobility-reproduction
Set-Location .\mobility-reproduction

2. Choose the exact experiment

Open the Experiment catalog, select the city, method, scale and version you want, and keep that record open. Each record brings together data links, setup commands, the run command, verification, expected results and recorded evidence. A homepage figure’s reproduction link selects its related records directly.

Use Show verified run commands only to start with workflows that have a recorded run and passing verification. Check the stated scope: a network construction check, a prepared-input replay and a full optimizer run establish different results. Workflows that are runnable but were not freshly verified, need external data, or only inspect historical evidence remain separately identified.

If the interactive catalog does not load, use the static experiment catalog. It preserves per-record setup, commands, evidence and limitations without JavaScript.

3. Set up the selected environment and inputs

Copy the selected record’s environment commands into a terminal at the extracted checkout root. Follow that record’s Python version, requirements file and any native build instructions; do not combine requirements files from different experiments. If external inputs are required, follow the listed provider links and expected hashes before running.

After Python is available, check the downloaded files:

py -3 -B tools/mcl_reproduction_check.py

The integrity check uses the Python standard library, makes no optimizer or network call, and checks the registered file hashes and archived receipts. It does not perform a fresh computation. For the run and verification commands, use the selected record’s environment interpreter.

Environment and platform notes

The standard recipes use Python 3.12. Historical Hong Kong FW, public prepared-input controls and several integrated workflows use separately specified Python 3.11 environments. Algorithm B requires the pinned tap-b build. Native Boston L3 has a separate exact environment lock and installation guide. The catalog specifies which setup applies.

Actual numerical validation was performed on Windows. A limited native Boston L3 clean-environment installation was validated; this is not a clean-install claim for every recipe. Most other runs used existing validated environments. On macOS/Linux, the usual forms are python3.12 -m venv .venv and .venv/bin/python, but the complete project has not been validated on those platforms. Native L3 is Windows-specific.

4. Run the computation

Copy the run command from the selected record. Use a new or empty output directory, and retain the record ID and directory for verification. The catalog chooses the registered command interface; you do not need to decide which historical catalog owns the experiment.

run performs the stated computation. inspect checks saved historical evidence and must not be used as a substitute for a new solve. A workflow may expose both actions; its record explains the difference and any scientific acceptance limits.

Optional first run: a small public ADMM control

This authored control is a quick way to exercise the download and verification workflow. It is not a Sioux Falls, Boston or Hong Kong city experiment. Use the exact catalog instructions when you move to a city result.

py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-tested.txt
.\.venv\Scripts\python.exe -B tools/mcl_reproduction_check.py --experiment admm-r2s-public-C1 --environment
.\.venv\Scripts\python.exe -B tools/mcl_reproduce.py run admm-r2s-public-C1 --output results/admm-r2s-public-C1
.\.venv\Scripts\python.exe -B tools/mcl_reproduce.py verify admm-r2s-public-C1 --run results/admm-r2s-public-C1

The result directory must be new or empty. Both commands must exit 0, and the result’s verification.json must report PASS with every required numerical check passing.

5. Verify and compare the expected result

Run the selected record’s verification command against the new result directory. Require a successful exit code and every required check to pass. Compare the documented objective, balances, capacities, gap or structural checks using that record’s fixed tolerances and expected outputs. Numerical reproduction means meeting these checks, not requiring a byte-for-byte identical floating-point file.

Keep the new run and verification receipts with the outputs. They record the inputs, code identity, environment and checks performed. An archived PASS receipt proves what was checked previously; it does not verify a new run. Where a scientific gate was not met, a historical inspection does not change that outcome.

What a successful reproduction covers. Downloading published frozen data and recomputing the documented result is a valid reproduction path. Prepared-input replays and structural checks retain their stated scope. They do not establish an untested raw-source acquisition or full four-stage pipeline.

Coverage and retained evidence

The Experiment catalog is the single reader-facing status list for all 108 records, including historical attempts and scope-only entries. Use each record’s current status and evidence, rather than adding counts from different delivery batches.

Original 41-command batch and actual executions

The original 41 verified command recipes map to 46 inventory records: 37 fresh-computation records and 9 bounded prepared-input replays. Their run and independent verification receipts are retained. These figures describe the original catalog, not the full integrated coverage.

In the earlier r12 delivery, 18 distinct commands were executed: 5 existing recipes from an extracted package, 4 exact Sioux recipes, 2 Boston prepared assignment replays, and 7 public prepared-input controls. Every run passed its independent checks; the seven controls were verified twice again. These used their own staged or extracted checkouts and existing validated Windows environments, not 18 runs from one identical ZIP or a new environment installation. The other 23 commands retain their earlier actual run provenance.

The two Boston S1/S2 semantic recipes rerun assignment only. The four exact Sioux P07 Lagrangian / R2_S ADMM recipes cover both 200 and 250 ODs; each has an actual fresh solve and original independent gate checks.

A run action may require external data or a specialized environment; availability is not a claim that every workflow was rerun.

Scientific and input limits that remain
  • The historical Sioux CG result has no independent full-graph pricing-closure certificate. Boston Lagrangian retains its original acceptance-gate limitation.
  • Hong Kong H1 finite-path/native-L3 and the independent 4-OD ADMM instance are separate from the verified Phase A/B static, 10-OD LP and 10-OD Lagrangian recipes.
  • The immediate GMNS provider revision for the frozen Sioux conversion snapshot remains unrecovered. The derived benchmark inputs retain the upstream academic-research use restriction and attribution; see data licenses and provenance.
  • Some source preparation workflows require exact external snapshots. A current upstream download can differ from a historical input. The record identifies the provider, expected hash and remaining requirements.
  • Raw-source acquisition, frozen-input computation and historical evidence inspection are distinct. Each record states the tested boundary; a published script alone does not establish a verified result.
Advanced: repository checkout and command interfaces

The compact ZIP is sufficient for registered computations. For the full website and project at this documentation release:

git clone -c core.autocrlf=false https://github.com/scholarhaozheng/mobility-network-lab.git
cd mobility-network-lab
git checkout reproduction-2026-10-04-r18
git rev-parse HEAD

The two established adapters remain available for scripts and historical receipts: tools/mcl_reproduce.py for the original registered recipes and tools/mcl_recovered.py for supplemental workflows. Both support record description, run and verification where enabled. The latter also provides explicit historical inspection. Prefer the exact commands supplied by the catalog; no new unified solver command or broader scientific claim is introduced by this documentation release.
